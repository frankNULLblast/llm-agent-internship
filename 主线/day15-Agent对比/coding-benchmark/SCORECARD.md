## 一、先定规则，再开跑（公平性五条）

违反任意一条，这次对比的数据就不能用。

0. **⚠ 必须开新会话拿 WorkBuddy 的答案**。这道题是当前这个 WorkBuddy 会话出的，它知道四个埋点分别埋在哪，让它直接作答等于开卷考试，数据没有意义。正确做法：**另开一个全新对话**，只粘贴题面，把那次的输出作为 WorkBuddy 的提交物。Kimi 那边同理，用干净的新对话，别在聊过这道题的上下文里问。
1. **同一段字符**。把 `TASK.md` 里「题面（复制这一段）」从第一个字到最后一个字整段复制，两边一字不差。不要自己补一句"注意偏移要对"——那等于泄题。
2. **单轮出题**。第一次回复即为提交物。不追问、不提示、不说"你这里有 bug"。
3. **允许一轮自查修复**（可选但两边必须一致）：如果要给修复机会，就统一只说一句「请自行检查并给出最终版本」，不指出任何具体问题，且只给一次。
4. **落盘方式一致**。把两边输出的代码分别存成两个目录，用同一个脚本跑：

```
submissions/
├── workbuddy/
│   └── minichunk/...
└── kimi-k3/
    └── minichunk/...
```

跑分：

```bash
cd 主线/day15-Agent对比/coding-benchmark
python verify_chunker.py submissions/workbuddy  --label WorkBuddy --out result_workbuddy.json
python verify_chunker.py submissions/kimi-k3    --label Kimi-K3   --out result_kimi.json
```

脚本自身可信度已验证：参考实现 **19/19**，人为劣化版（加了 `strip()` + 硬编码工厂）**14/19**，三个关键埋点全部被抓出来。

## 四、结论怎么写才站得住

写结论时避开两个坑：

**别说"谁更强"**。一道题、一次采样，得不出这个结论。要说的是「在这道题上，A 在 X 项契约上通过而 B 没有，差异出在 Y」。

**要区分"没做到"和"没想到"**。同样是 C05 偏移回切失败，一种是它压根没意识到这条契约（测试里也没测），另一种是它意识到了但实现有 bug（测试里测了但自己也没跑）。前者是设计意识问题，后者是工程细节问题，答辩时讲清楚这个区别，比报个分数有价值得多。

**建议附一段真实差异样本**。像主线 Day20 那次 `flash` vs `pro` 的发现一样——把两边同一处的代码贴出来对比，比任何分数都有说服力。
